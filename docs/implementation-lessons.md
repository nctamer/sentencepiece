# Implementation Lessons: What Went Wrong and How to Avoid It

This document records failures from the first attempt at implementing `split_by_interval` in sentencepiece (June 2026), and prescribes rules for any future implementation work on this codebase.

## Failures

### 1. Manually patched generated protobuf files incorrectly

**What happened**: Edited `src/builtin_pb/sentencepiece_model.pb.h` (5030 lines) and `.pb.cc` (3499 lines) by hand. Guessed at `_has_bits_` bitmask values, wire format tag numbers, serialization logic. The resulting model files could not be loaded back — `spm_encode` and the Python `sentencepiece` package both rejected them with "could not parse ModelProto."

**Root cause**: These files are machine-generated by `protoc`. They have complex internal invariants (field ordering in serialization, bitmask allocation, cached size tracking) that cannot be correctly maintained by hand-editing.

**Rule**: NEVER manually edit `src/builtin_pb/*.pb.h` or `*.pb.cc`. Instead:
1. Identify the protoc version: `grep "Generated by the protocol buffer compiler" src/builtin_pb/sentencepiece_model.pb.h`
2. Install matching protoc
3. Edit ONLY `src/sentencepiece_model.proto`
4. Regenerate: `protoc --cpp_out=src/builtin_pb/ src/sentencepiece_model.proto`
5. Verify the diff is minimal and expected
6. Build and run tests before any other changes

If protoc regeneration produces a large diff (different protobuf version), evaluate whether the build still works. If not, find the exact matching version.

### 2. Made all changes at once, tested nothing until the end

**What happened**: Modified 9 files simultaneously (proto, pb.h, pb.cc, model_interface.h, model_interface.cc, trainer_interface.cc, unigram_model_trainer.cc, spec_parser.h, spm_train_main.cc). Then tried to train a model. Got garbage results (85 sentences loaded, model unloadable). No way to isolate which change caused which failure.

**Root cause**: No incremental validation. Each file change introduced potential bugs, and they compounded.

**Rule**: One logical change at a time, with a build+test gate between each:
1. Add proto field → build → verify flag appears in `spm_train --help`
2. Add logic to `SplitIntoWords()` → build → write a unit test or small script that calls it
3. Add logic to `IsValidSentencePiece()` → build → verify with a training run on tiny corpus
4. Never move to step N+1 until step N produces correct output

### 3. Did not understand sentencepiece's training pipeline before modifying it

**What happened**: 
- Assumed `SplitSentencesByWhitespace()` is always called. It's not — it's gated by `if (trainer_spec_.split_by_whitespace())` in both BPE and unigram trainers.
- Assumed the unigram trainer calls `SplitSentencesByWhitespace()` before seed generation. It's actually called AFTER (line 624 is after line 619 `MakeSeedSentencePieces()`).
- Did not realize `max_sentence_length=4192` (default) would silently drop all scores longer than ~4KB.

**Root cause**: Read function signatures but not the actual call graph. Made assumptions about execution order without tracing it.

**Rule**: Before modifying any function, trace its callers:
```bash
grep -rn "FunctionName" src/ --include="*.cc" | grep -v test
```
Read the calling context (10 lines before and after the call site). Understand:
- When is it called? (conditionally? always?)
- What state does it expect? (what's in `sentences_` at that point?)
- What state does it produce? (does it replace `sentences_`?)

Document the call graph in a comment before writing code:
```
// Call graph for BPE training:
//   Train() → LoadSentences() → SplitSentencesByWhitespace() [if split_by_whitespace]
//           → pretokenizer/delimiter insertion → symbol init → BPE merge loop
```

### 4. Did not study the existing working implementation before building a new one

**What happened**: The existing tokenizer (`paper-attacca/figures/assets/tokenizer.model`) was trained with `split_by_whitespace=false` and a corpus preprocessed by `build_corpus.py` (one moment per line). This achieves cross-whitespace tokens without any sentencepiece modification. I didn't discover this until the user pointed it out.

**Root cause**: Jumped to implementation without understanding the prior art in the same codebase.

**Rule**: Before implementing a feature, find and study every existing implementation of similar behavior:
```bash
find /Users/nctamer/repos -name "*.py" -o -name "*.sh" | xargs grep -l "sentencepiece\|spm_train" 2>/dev/null
```
Read how the existing system works end-to-end. Understand WHY it was built that way. Only then decide whether a new approach is better and what exactly it improves.

### 5. Confused the `▁` (U+2581) vs `Ġ` (U+0120) conventions

**What happened**: Claimed tokens would look like `▁PR:▁C5` when using ByteLevel encoding. Actually ByteLevel produces `Ġ` (GPT-2 convention), not `▁` (sentencepiece convention). The `Split` pretokenizer with `behavior="isolated"` + ByteLevel makes spaces into standalone `Ġ` tokens between words, NOT prefixes on the following word.

**Root cause**: Did not test the actual pretokenizer behavior on a sample before making claims.

**Rule**: Before claiming how a pretokenizer/normalizer behaves, test it:
```python
from tokenizers import Tokenizer
from tokenizers.pre_tokenizers import Split, ByteLevel, Sequence
from tokenizers import Regex

pre = Sequence([Split(pattern=Regex(r'\S+'), behavior='isolated', invert=False), ByteLevel()])
result = pre.pre_tokenize_str("hello world")
print(result)  # See EXACTLY what it produces
```

Never describe behavior from documentation or memory alone.

### 6. Said "yes I can do this" without understanding the hardest part

**What happened**: Confidently proposed implementing merge inheritance in sentencepiece's BPE trainer without understanding the `Symbol` data structure, the `active_symbols_` tracking, or the `AcceptSymbol()` merge procedure. When it came time to implement, realized the force-apply logic requires interacting with a complex position-tracking system.

**Root cause**: Estimated difficulty from the algorithm description ("just iterate and merge pairs") without examining the actual data structures.

**Rule**: Before committing to implement a complex feature:
1. Read the data structure definitions it will touch
2. Read at least one existing function that modifies those structures (e.g., `AcceptSymbol()`)
3. Write pseudocode showing exactly how the new code interacts with existing structures
4. If you cannot write the pseudocode confidently, say so — and propose studying it further or prototyping in Python first

## Summary Checklist for Any Agent Implementing sentencepiece Changes

- [ ] Identified protoc version and regeneration procedure (do NOT manually edit pb files)
- [ ] Traced the call graph of every function being modified
- [ ] Tested the current behavior on a small sample BEFORE making changes
- [ ] Making ONE change at a time with build+test between each
- [ ] Studied existing implementations of similar behavior in the codebase
- [ ] For complex features: read the data structures, wrote pseudocode, and verified against actual code
- [ ] Set `--max_sentence_length` appropriately for the corpus (default 4192 is too small for music scores)
- [ ] When adding new proto fields: verified the model can be saved and reloaded before adding logic
- [ ] Never described pretokenizer/encoder behavior without testing it on actual input
